# Creative OS · Фаза A1 — бриф для разработки

Этот файл читается первым. Он же кладётся в репозиторий как `CLAUDE.md`.

---

## Что строим

Библиотеку рекламных креативов Meta, склеенную со сквозной воронкой до сделки, с автоматической диагностикой каждого объявления. Без AI-слоя.

## Чего НЕ строим в A1 — важнее, чем что строим

Всё перечисленное отложено сознательно. Если агент начинает это делать — остановить:

- ❌ vision-анализ, OCR, эмбеддинги, любые вызовы LLM
- ❌ атрибутная регрессия и статистика по атрибутам
- ❌ генератор гипотез
- ❌ автозаполнение `evidence` (таблица создаётся, заполняется руками)
- ❌ Google Ads, TikTok, любая вторая платформа
- ❌ видео как отдельный трек
- ❌ real-time апдейты чаще, чем раз в 4 часа

Поля и таблицы под всё это в схеме **есть с первого дня** и стоят пустыми. Это осознанно: решения схемы дорого разворачивать назад, механика — дёшево доделать потом.

## Жёсткое правило порядка

**Интерфейс не начинается, пока не пройден гейт из `06-GATE.md`.**

Гейт — это сверка цифр системы с рекламным кабинетом и CRM вручную. Пока она не сходится, любой дашборд показывает красивую неправду. Соблазн начать с интерфейса будет сильный, потому что его видно, а склейку — нет.

Порядок: `T0 → T1 → T2 → T3 → T4 → ГЕЙТ → T5…T10`.

## Стек

| Слой | Выбор | Замечание |
|---|---|---|
| БД | Postgres 15+ (Supabase) | `pgvector` включить сразу, использовать в A2 |
| Язык | Python 3.12 | зависимости через `uv` |
| Meta API | прямые вызовы Graph API через `httpx` | **не** `facebook-business` SDK: объектная модель непредсказуема при генерации кода, версии ломаются |
| Расписание | GitHub Actions cron, каждые 4 часа | бесплатно, версионируется, логи из коробки |
| Хранилище ассетов | Supabase Storage, ключ = `sha256` | дедуп бесплатно |
| Интерфейс | Next.js на Vercel, одна страница | только после гейта |
| Миграции | нумерованные `.sql` файлы, применяются по порядку | без ORM-миграторов |

Никакого ORM. Сырой SQL через `psycopg`. Причина: вся ценность системы в метриках, а метрики должны читаться человеком в `.sql`, а не собираться из билдера.

## Переменные окружения

```
DATABASE_URL=postgresql://...
META_ACCESS_TOKEN=            # System User token, НЕ пользовательский
META_API_VERSION=v21.0
META_AD_ACCOUNT_IDS=act_...,act_...
META_APP_SECRET=              # для appsecret_proof
CRM_BASE_URL=
CRM_API_KEY=
SUPABASE_URL=
SUPABASE_SERVICE_KEY=
SETTLED_WINDOW_DAYS=7
RESTATEMENT_WINDOW_DAYS=14
```

Про токен: нужен **System User token** из Business Manager с правами `ads_read`. Пользовательский токен протухнет через 60 дней и уронит крон в самый неудобный момент. Это делается один раз руками и относится к задаче T0.

## Инварианты, которые нельзя нарушать

1. **Единица перформанса — `exposure`, а не `asset`.** Один визуал живёт в нескольких вариантах, один вариант — в нескольких объявлениях. Вердикты выносятся по экспозиции.
2. **`fact_daily` только добавляется, никогда не обновляется.** Каждый синк пишет строки с новым `as_of`. Meta переписывает конверсии задним числом до 7 дней — снимки нужны, чтобы это видеть.
3. **Решения принимаются только на устоявшихся данных** (`day <= current_date - SETTLED_WINDOW_DAYS`).
4. **Ни один порог не хардкодится в коде.** Всё в таблице `config`.
5. **Каждый запуск синка пишет строку в `sync_run`.** Молчаливо упавший крон — самый частый способ потерять две недели.
6. **`platform` заполняется всегда**, даже когда значение одно.

## Определение готовности A1

Одновременно выполнено:

- крон работает 7 дней подряд без ручного вмешательства;
- гейт из `06-GATE.md` пройден и перепройден через неделю;
- матч-рейт лидов до экспозиции ≥ 80 %;
- еженедельные решения по креативам принимаются из интерфейса, без Ads Manager;
- у каждой запущенной экспозиции заполнено поле гипотезы.
